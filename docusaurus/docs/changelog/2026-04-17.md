## Also today: Nextcloud uid mapping fix

Nextcloud (LXC 212) was showing _"Your data directory is invalid / not
writable"_ after the VM → LXC migration. Root cause: the LXC is
**unprivileged** but the NAS data dir was still owned by host uid 33.
Unprivileged LXCs map container uid 33 → host uid **100033**.

Fix on node3:

```bash
chown -R 100033:100033 /mnt/nas/nextcloud
```

Immich didn't hit this because its NAS dirs are `chmod 777`.

Wrote this up as:

- [Unprivileged LXC uid mapping](../unprivileged-lxc.md): the concept

## Prometheus data directory permissions fix

Uptime Kuma showed Prometheus as down (connection refused). SSH'd in and checked the container logs, which revealed a crash loop due to a permissions error on `/prometheus/queries.active`.

Prometheus runs internally as the non-root `nobody` user (UID `65534`). The `/data/prometheus` volume mount on the host LXC was owned by `root:root`, preventing the container from writing to it.

**Fix:**

- Connected to the LXC (`10.0.1.18`) and ran `chown -R 65534:65534 /data/prometheus`
- Restarted the Docker container
- Updated `ansible/playbooks/prometheus.yml` to automatically ensure the `/data/prometheus` directory is created with `owner: "65534"` and `group: "65534"` before deploying.

## Uptime Kuma monitor DNS fix

Internal-only services (Grafana, Semaphore, AdGuard, Docs, Portainer, Proxmox UIs) were returning 404 in Uptime Kuma. Root cause: the uptime-kuma LXC uses public DNS (not AdGuard), so `*.example.com` domains that are only in AdGuard rewrites don't resolve to Caddy internally.

Services accessible via Cloudflare tunnel (Authentik, Immich, Nextcloud) resolved correctly via public DNS and were already green.

**Fix:** Updated all internal-only monitors in `setup_monitors.py` to use direct LXC IP:port instead of public domain names. Updated idempotency logic to detect URL mismatches and delete+recreate affected monitors.

| Before                          | After                                |
| ------------------------------- | ------------------------------------ |
| `https://grafana.example.com`   | `http://10.0.1.19:3000`              |
| `https://portainer.example.com` | `https://10.0.1.12:9443` (ignoreTls) |
| `https://pve1.example.com`      | `https://10.0.0.10:8006` (ignoreTls) |
| …                               | …                                    |

**Files touched:** `services/core/uptime-kuma/setup_monitors.py`, `docusaurus/docs/stack/uptime-kuma.md`

**Gotcha:** `uptime-kuma-api` `edit_monitor` wasn't used: simpler to delete + recreate since monitors were brand new (no history to preserve).

## Security hardening

Ran a security audit across the stack. Findings and fixes:

### SSH hardened on all LXCs and Proxmox nodes

New playbook `ansible/playbooks/harden-ssh.yml` deployed to all 16 reachable hosts:

- `PasswordAuthentication no`: SSH is now key-only; password brute-force not possible
- `PermitRootLogin prohibit-password`: root SSH requires key (already the Debian default, now explicit)

Hosts unreachable (legacy VMs / unprovisioned LXCs): `core-services`, `prod-services`, `test-services`, `coolify`, `n8n`. Apply when those are provisioned.

### Grafana .env corrected

`services/core/grafana/.env` had `changeme` as the password. The actual admin password was reset via CLI after first boot, but if the container had ever been recreated it would have reverted. Fixed to match the real credential. Live `.env` on the LXC also updated.

### Outstanding risks (not yet fixed)

| Risk                                                                    | Mitigation needed                                 |
| ----------------------------------------------------------------------- | ------------------------------------------------- |
| No Authentik SSO on Portainer, Semaphore, Grafana, AdGuard, Proxmox UIs | Add Caddy `forward_auth` → Authentik outpost      |
| `node_exporter` unauthenticated on `:9100` on all LXCs                  | iptables rule limiting to Prometheus scraper only |
| Prometheus unauthenticated on `:9090`                                   | Basic auth or network restriction                 |
| No rate limiting on public login pages                                  | Cloudflare WAF rule on auth/immich/nextcloud      |
| No 2FA enforced on Authentik                                            | Enable in Authentik policy                        |

## CI/CD runner SSH key fix

GitHub Actions deploy job was failing with exit code 4 (Ansible unreachable) on every push that touched `docusaurus/`. Root cause: the github-runner LXC has its own SSH key pair (`github-runner@homelab`) that was never added to any LXC's `authorized_keys`; Terraform only injects the Mac's key at provision time.

**Files touched:**

- `ansible/playbooks/authorize-runner.yml`: new playbook; adds runner pubkey to all hosts via `authorized_key` module. Idempotent.
- `AGENT.md`: added `authorize-runner.yml` as a required step in the "add new service" workflow

Runner key pushed to all 16 active LXCs and Proxmox nodes. Future LXCs: run `ansible-playbook playbooks/authorize-runner.yml -l <service>` after provisioning.
