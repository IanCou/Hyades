# 2026-05-24: macOS Tahoe VM, prod-services & Windows11 cross-node migrations

**Sun, May 24, 2026.** First non-LXC workload provisioned in the cluster:
a macOS Tahoe (26) VM on node2 using the [LongQT-sea/OpenCore-ISO](https://github.com/LongQT-sea/OpenCore-ISO)
bootloader image. Also rebalanced two existing VMs to free space on node3.

## VM 401: macOS Tahoe on node2

### Why node2

Initial target was node3, but `local-lvm` there had only ~18 GB physical
free (67.97% used). With thin overprovisioning a 64 GB virtual disk would
fit on paper, but a real macOS install (~15–20 GB used) would push the
pool over and risk LXCs 211/212/213 sharing it. node2 had 110 GB free on
`local-lvm`; picked that instead.

### Specs

| Setting         | Value                                                 |
| --------------- | ----------------------------------------------------- |
| VMID            | 401                                                   |
| Name            | `macOS-test`                                          |
| Machine         | q35                                                   |
| BIOS            | OVMF (UEFI), no Pre-Enroll Keys (Secure Boot off)     |
| CPU             | `Skylake-Client-v4,vendor=GenuineIntel` (via `-args`) |
| Cores / sockets | 2 / 1                                                 |
| RAM             | 4 GB, ballooning off                                  |
| scsihw          | virtio-scsi-single                                    |
| sata0           | `local-lvm:vm-401-disk-1`, 64 GB, ssd=1, discard=on   |
| net0            | virtio, vmbr0                                         |
| ide2            | `LongQT-OpenCore-v0.7.iso` (boot first)               |
| Guest agent     | enabled                                               |

### CPU note

Host is an Intel i5-8500 (Coffee Lake, AVX2 only, no AVX-512). The
LongQT README lists `Skylake-Server-v4` (AVX-512) and `Skylake-Client-v4`
as recommended models for macOS 10.11–26; AVX-512 is optional, not
required, so Client-v4 is correct here. The CPU must be set via `-args`
on macOS 13+ to override Proxmox defaults (`+kvm_pv_eoi,+kvm_pv_unhalt`
prevent boot on AMD; not strictly needed on Intel but matches the
documented workflow).

### Recovery ISO workflow

The upstream [macos-iso-builder](https://github.com/LongQT-sea/macos-iso-builder)
took down all prebuilt recovery ISOs for legal reasons (v26 release has
zero assets). Sourced the recovery image directly from Apple via
Acidanthera's [`macrecovery.py`](https://github.com/acidanthera/OpenCorePkg/tree/master/Utilities/macrecovery):

```bash
# On node2
apt-get install -y xorriso dmg2img
mkdir -p /root/macrecovery && cd /root/macrecovery
curl -sSL -O https://raw.githubusercontent.com/acidanthera/OpenCorePkg/master/Utilities/macrecovery/macrecovery.py
curl -sSL -O https://raw.githubusercontent.com/acidanthera/OpenCorePkg/master/Utilities/macrecovery/boards.json

# Mac-A61BADE1FDAD7B05 is one of the "latest" boards in boards.json (currently → Tahoe)
python3 macrecovery.py -b Mac-A61BADE1FDAD7B05 -m 00000000000000000 -os latest download
# → com.apple.recovery.boot/BaseSystem.dmg (914 MB) + BaseSystem.chunklist
```

First attempt: packaged the files into an ISO9660 image with `xorriso`
and attached as `ide0`. **OpenCore did not detect the recovery entry**
on the main picker; only "Reset NVRAM" and "Toggle SIP" showed up.
OpenCore's scanner doesn't reliably pick up `com.apple.recovery.boot/`
from ISO9660.

Working approach: convert the DMG to a raw image and attach as a virtual
**disk** instead. OpenCore reads the APFS container inside and surfaces
a "macOS Base System" boot entry:

```bash
dmg2img com.apple.recovery.boot/BaseSystem.dmg /root/macrecovery/BaseSystem.img
# 914 MB DMG → 2.5 GB raw
qm importdisk 401 /root/macrecovery/BaseSystem.img local-lvm --format raw
qm set 401 --sata1 local-lvm:vm-401-disk-2
qm set 401 --boot 'order=ide2;sata0;sata1'
```

Boot order: OpenCore CD → target disk → recovery disk. Picker now shows
"macOS Base System" entry. Install proceeds via standard Recovery →
Disk Utility (erase sata0 as APFS / GUID) → Reinstall macOS Tahoe.

> **Caveat:** `dmg2img` writes all sectors, so the raw img is fully
> allocated on local-lvm (not thin-friendly). Delete sata1 + the
> `vm-401-disk-2` LV after install completes to reclaim ~2.5 GB.

### Outstanding post-install steps

Tracked in [Post-install: macOS on Proxmox](../runbooks/macos-vm) runbook:

- Mount target disk EFI partition and copy `EFI_RELEASE/EFI` from the
  OpenCore CD so the VM boots without the OpenCore ISO attached.
- Install VMHide.kext for iCloud/iServices on macOS 15+/26.
- Tahoe cursor freeze workaround: append `-device virtio-tablet` to the
  existing `-cpu Skylake-Client-v4,vendor=GenuineIntel` args (don't
  overwrite: `qm set --args` replaces the whole string).

## VM 201 (prod-services): node3 → node1

Stopped legacy VM with a 32 GB scsi0 disk. Migrated to free up node3 for
the Windows VM rebalance. CD media (`local:iso/debian-13.3.0-amd64-netinst.iso`)
detached first since `local` storage content differs per node.

```bash
ssh root@10.0.0.12 "qm set 201 --ide2 none,media=cdrom"
ssh root@10.0.0.12 "qm migrate 201 node1 --with-local-disks"
```

Duration **5m 10s** at 112 MB/s. Note this transfers the full 32 GB
allocation, not just used blocks (qm migrate's local-disk path uses
`qemu-img convert` end-to-end, ignoring thin sparseness).

## VM 400 (Windows11): node2 → node3

Stopped. Disks: `efidisk0` (4 MB), `scsi0` (64 GB), `tpmstate0` (4 MB),
all on local-lvm. Migrated after the prod-services move freed ~30 GB on
node3.

```bash
ssh root@10.0.0.11 "qm migrate 400 node3 --with-local-disks"
```

Duration **11m 55s**.

**Storage delta:**

| Pool              | Before (this session) | After                                             |
| ----------------- | --------------------- | ------------------------------------------------- |
| node1 `local-lvm` | 27.89%                | ~35% (added 32 GB Windows-free, but +201's 32 GB) |
| node2 `local-lvm` | 25%                   | 30.56% (added 401's macOS disks, removed 400)     |
| node3 `local-lvm` | 67.97%                | 71.19% (removed 201's 32 GB, added 400's 64 GB)   |

node3 is back near 71% used; the Windows VM offsets the prod-services
removal. Worth watching as the macOS install on node2 fills out.
