# 2026-07-25: Kavita + Audiobookshelf, Tailscale/LAN-only

Provisioned two new prod-tier ebook/audiobook services. Original ask was
"Calibre (web)", narrowed after comparing options: Calibre/calibre-web both
assume an existing Calibre library (`metadata.db` + its own folder layout),
which meant a one-time import step for a batch of plain EPUB files already on
hand. Went with folder-scan readers instead, no import step required:

- **Kavita** (`jvmilazz0/kavita:latest`): ebook/manga/comic reader, scans a
  directory tree directly.
- **Audiobookshelf** (`ghcr.io/advplyr/audiobookshelf:latest`): audiobook/podcast
  server with progress tracking.

## Provisioning

Both scaffolded via `make new-service name=<x> tier=prod node=node1`, node1
chosen over node2/node3 on live headroom (`free -h` showed node1 at 16Gi
available vs. ~2-3Gi on the other two; `hardware.md`'s "8GB per node" is
stale, node1 has since been upgraded to 23GB).

| Service        | LXC | IP        | Port                       |
| -------------- | --- | --------- | -------------------------- |
| kavita         | 219 | 10.0.2.18 | `:5000`                    |
| audiobookshelf | 220 | 10.0.2.19 | `:13378` (container `:80`) |

Both 2 cores / 2 GB / 20 GB: scaffold defaults, no special resource needs.

## Access posture: Tailscale/LAN only, no public exposure

Neither service has a public DNS record or a Cloudflare Tunnel ingress rule.
Same posture as AirTrail/Cobalt. Caddy fronts both with a real TLS cert
(wildcard `*.example.com`) and AdGuard resolves the hostnames internally,
so they're reachable from the LAN and from any device on the Tailscale subnet
router (LXC 116), but not from the public internet. This was the explicit
ask ("accessible via Tailscale"); no extra Tailscale-specific config was
needed since the subnet router already advertises `10.0.0.0/22`;
provisioning a prod LXC and skipping the public-DNS step (which isn't
automated in this repo anyway) was sufficient.

## Gotcha found

`playbooks/prometheus.yml` syncs the config file but never restarts/reloads
the container, and the compose file doesn't set `--web.enable-lifecycle` for
a `/-/reload` hit either; new scrape targets silently don't take effect
until something restarts the container by hand. Worth adding
`--web.enable-lifecycle` + a reload step to the playbook next time it's
touched; didn't do it here to keep this change scoped to the two new
services.
