**Real vs. thin-virtual free space, revisited:** double-checked node1's `local-lvm` headroom before creating either resource. `pvesm status` reports ~204 GB "available" for the pool; `vgs pve` reports only 16 GB `VFree`. These answer different questions: VFree is unallocated-from-the-VG headroom (matters only for growing the pool itself or making an unrelated new LV); the pool's own Available is what actually gates new thin-volume writes inside it, and that's the number that mattered here. Worth a clearer callout in `AGENT.md`'s existing thin-pool gotcha so this isn't re-litigated next time.

## VM 400: Windows11 (node1), re-provisioned

The pre-07-11 VM 400 was gone with no disks to resume from; this is a fresh install, not a restore. Copied `Win11_25H2_English_x64.iso` + `virtio-win.iso` from node2's `local:iso` (Proxmox local storage isn't shared across nodes) via direct node-to-node `scp`, then:

```bash
qm create 400 --name Windows11 --machine q35 --bios ovmf \
  --efidisk0 local-lvm:1,efitype=4m,pre-enrolled-keys=1 \
  --tpmstate0 local-lvm:1,version=v2.0 \
  --cpu host --sockets 1 --cores 4 --memory 8192 --balloon 0 \
  --scsihw virtio-scsi-single --scsi0 local-lvm:80,ssd=1,discard=on \
  --net0 virtio,bridge=vmbr0 \
  --ide2 local:iso/Win11_25H2_English_x64.iso,media=cdrom \
  --ide3 local:iso/virtio-win.iso,media=cdrom \
  --boot order='ide2;scsi0' --agent enabled=1
```

**`pre-enroll-keys` isn't the right property name on pve-manager 9.1.9**; it's `pre-enrolled-keys` (confirmed against VM 401's working macOS efidisk0 config, which already used it). `qm create` fails fast with a schema error if you get this wrong, so it's a quick fix, not a silent misconfiguration. Noting it here to save the lookup next time.

Placed on node1 instead of node2/node3 (where the original VM 400 lived): node1 has 24 GB RAM and ~17 GB free; node2 and node3 are both RAM-constrained (7.5 GB total each, 1-4.5 GB free) with tight physical `local-lvm` headroom (~15-16 GB VFree apiece) besides.

Still to do post-install (tracked manually, no runbook yet; consider writing one if a third Windows/macOS-class VM ever gets provisioned): load the `vioscsi` driver during install for the disk to be visible, install `NetKVM` + `virtio-win-guest-tools.exe` for network + guest agent, confirm whether the ISO is Pro or Home edition (Home can't accept inbound RDP), and set a DHCP reservation + `EXTRA_HOSTS` entry in `scripts/adguard_rewrites.py` once its IP is known.

## Claude Code browser control: same-machine constraint confirmed

`claude-in-chrome` (the `mcp__claude-in-chrome__*` tool family) pairs Claude Code to Chrome via Chrome's Native Messaging Host protocol: stdio between a locally-spawned process and the browser, not a network socket. Not bridgeable over SSH port-forwarding. A Claude Code session on `dev` cannot drive Chrome on the Mac; use a separate local Claude Code session on the Mac for anything needing browser control, or (not done here) run a headed Chrome + Xvfb/VNC stack on the LXC itself for true co-located parity.
