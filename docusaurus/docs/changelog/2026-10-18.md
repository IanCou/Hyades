# 2026-10-18: CI deploy skip group, inventory-rendered Prometheus targets

## What broke

CI run `39100257683` (push to `main`, commit `8b1e7e5`) failed in the `deploy` job,
step "Deploy changed services", with `SERVICES="node-exporter prometheus"`.
`playbooks/node-exporter.yml` targets all of `docker_hosts`, and 4 came back
UNREACHABLE:

| Host               | IP        | Why                                                       |
| ------------------ | --------- | --------------------------------------------------------- |
| immich             | 10.0.2.10 | LXC 211, stopped in Proxmox on purpose                    |
| nextcloud          | 10.0.2.11 | LXC 212, stopped on purpose                               |
| internship-watcher | 10.0.3.11 | LXC 602, stopped on purpose                               |
| raspberrypi        | 10.0.0.3  | running, but the self-hosted runner has no SSH path to it |

The step's shell runs with `bash -e`, so the failure ended the loop and
`prometheus` never deployed. The `--storage.tsdb.retention.size=12GB` cap from
`8b1e7e5` was never applied. Any later change touching node-exporter, or a
service on one of those hosts, would have failed the same way.

## Fix 1: `ci_deploy_skip` inventory group

New top-level group in `ansible/inventory/hosts.yml` with two children:

- `stopped`: empty in git. The deploy job's first step,
  `scripts/proxmox_power_state.py`, SSHes to the Proxmox nodes in order, reads
  `pvesh get /cluster/resources --type vm`, and writes an inventory fragment
  listing every inventory host whose guest isn't running. Later steps load it
  through `ANSIBLE_INVENTORY`. If no node answers, the job fails before any
  host is touched. Today that is immich, nextcloud, internship-watcher
  plus the stopped legacy and desktop VMs.
- `ci_unreachable`: raspberrypi, by hand (not a Proxmox guest).

Hosts keep their vars and tier groups, and manual runs
(`ansible-playbook playbooks/deploy.yml -l immich`) still work. Powering an LXC
on or off needs no repo edit.

In `ci.yml`, every `ansible-playbook` call in the deploy job now excludes the group:

- Per-service playbooks: `-l 'all:!ci_deploy_skip'`. If the play matches no hosts
  after that, ansible prints `skipping: no hosts matched` and exits 0 (checked:
  `internship-watcher.yml`).
- `deploy.yml`: `-l "$service:!ci_deploy_skip"` leaves no hosts in the whole
  inventory for a skipped service, and ansible-playbook treats that as an
  error (exit 1). So the loop first checks `ansible "$service:&ci_deploy_skip"
--list-hosts`. A member gets a `::notice::` and is skipped. A service
  missing from inventory still fails loudly, as before.
- `docs.yml` takes the same limit for consistency (docs is not in the group).

The loop no longer stops at the first failure. Each failing service is
recorded and the rest still deploy. Skipped hosts never reach a playbook, so
any failure is on a host that is powered on: the step then emits
`::error::deploy failed for: <list>` plus a "Deploy failures" list in the run
summary and exits 1. With no failures the job is green, and the skipped hosts
are listed in a `::notice::` and the run summary.

## Fix 2: Prometheus targets rendered from inventory

`services/core/prometheus/prometheus.yml` was a hand-kept static target list
and had drifted from the inventory. Probing `:9100` showed 6 hosts answering
HTTP 200 that were never scraped. They are now scraped:

| Host          | Target         | Job        |
| ------------- | -------------- | ---------- |
| speedtest     | 10.0.1.23:9100 | `core`     |
| searxng       | 10.0.2.13:9100 | `prod`     |
| homeassistant | 10.0.2.22:9100 | `prod`     |
| kafka         | 10.0.3.12:9100 | `test`     |
| dev           | 10.0.3.14:9100 | `test`     |
| raspberrypi   | 10.0.0.3:9100  | `gateways` |

Replaced it with `prometheus.yml.j2`, still under `services/core/prometheus/` so
CI's change detection maps it to the `prometheus` service:

- One job per inventory group. The old job names (`proxmox`, `core`, `prod`,
  `test`, `ntfy`) are kept so Grafana dashboards keep matching. `runners`
  (github-runner) folds into `core`, where it was already scraped. `gateways`
  is new.
- Each target is `ansible_host:9100` with a `host` label holding the inventory
  name. `instance` stays the default IP:port, so existing selectors still match.
- The 3 `stopped` LXCs are no longer scraped, so `up == 0` keeps meaning
  "broken". This also removes the `test` job's stale `db-stack` comment on
  `.3.11`. Bastions, legacy VMs and desktop VMs stay out (no `node_exporter`
  verified on them).
- Scrape groups are looked up strictly, so a renamed group fails the render
  instead of silently dropping a tier.
- CI now adds `prometheus` to the deploy list whenever
  `ansible/inventory/hosts.yml` changes. Without that, an inventory-only edit
  would change the rendered targets and never ship them.
- `validate` renders the template against the real inventory and runs
  `promtool check config` whenever `prometheus` is in the changed set.
  `--syntax-check` never renders templates.

`ansible/playbooks/prometheus.yml` now uses `template` instead of `copy` (compose
is still copied). It runs `promtool check config` as the template's `validate:`,
so a bad render never replaces the live file. When the rendered file changes,
a handler sends `SIGHUP`, because a bind-mounted file change does not recreate the
container and the new targets would otherwise never load. A second handler
waits until Prometheus's `prometheus_config_last_reload_successful` is 1 and
its success timestamp is newer than the play's start. A failed reload is
otherwise silent, since Prometheus keeps the old config. I used SIGHUP rather
than `--web.enable-lifecycle`, which would expose an unauthenticated
`/-/reload` and `/-/quit` on `:9090`. This closes the "Prometheus config
reload" item in `progress.md`.

## Deploy note

This merge touches `services/core/prometheus/` and the inventory, so the deploy job
runs `prometheus.yml`. That ships the new targets and finally applies the
`--storage.tsdb.retention.size=12GB` cap from `8b1e7e5`. The compose change
recreates the container, which loads the new config on start.

## Gotchas

- `ansible-playbook -l` treats a limit that leaves the whole inventory empty
  as a hard error (exit 1). A limit that only leaves one play empty is a
  skip (exit 0). The deploy loop handles the two cases differently.
- `scripts/audit_infra.py` still SSHes into the stopped LXCs and reports
  them UNREACHABLE. Teaching it to use `proxmox_power_state.py` is a follow-up.
- `stopped` is only filled in CI. A manual `ansible-playbook
playbooks/prometheus.yml` sees it empty and scrapes stopped guests (they
  show `up == 0`) until the next CI deploy of Prometheus.

## Cached public observability summary

Added `services/core/prometheus/observability/` with a standard-library Python
collector. The Prometheus Compose stack and playbook run it as an unprivileged, read-only container and restart it when its
bind-mounted code/config changes. Caddy exposes only the fixed overview path on
the metrics hostname. Network tables, stack docs, `AGENT.md`, and `progress.md` describe the new route and rollout.

CPU, memory, root-filesystem capacity, and observed 24-hour scrape availability
come from Proxmox host exporters only. Public service checks use an explicit
HTTPS allowlist without following redirects or resolving private addresses.
Cache values expire after five minutes; errors never produce invented healthy
states or reveal upstream addresses. No backup status is claimed, no raw query
API is exposed, and no credentials are needed by the browser.

The Cloudflare Tunnel hostname, actual host metrics, CORS origins, and public
probe behavior still require operator verification before the portfolio goes
live. This change does not configure external tunnel state or deploy itself.
